# Original feature audit

**Updated:** 2026-10-14  
**Purpose:** establish what the original actually offers, what `v2` currently implements, and what “parity” still means before more features are built.

## How this audit was made

I compared the original app's built-in Arabic guide in the root `index.html` (chapters 1–7, approximately lines 1870–2015) with the actual app shell and reader engine. Most of the reader engine is embedded as Base64 in the element `#engine`; its internal section comments identify features such as `شريط الفقرة`, `شريحة التحديد`, `اللوحة الجانبية`, `الإحالات بين الفقرات`, `إحصاءات القراءة`, and `القلم ومربعات النص`. I then checked the corresponding `v2/src` UI, domain, importer, and storage code.

The guide is evidence of the original product promise, not proof that every advertised path is bug-free. Known user observations are recorded separately below. Likewise, an implementation in v2 is not “verified parity” until its full interaction is exercised in a browser and compared with the reference.

## Corrections to the feature ledger

1. **“Pin” is not a generic bookmark in the original.** The paragraph toolbar's 📌 action adds the passage to the cross-book link tray. Iteration 22 assigns that behavior to the toolbar; old quick-pin records remain accessible separately so an upgrade does not discard saved data.
2. **The original has a two-ended link relation.** It renders a navigation chip at both passages and removes the relation from either end. Iteration 23 data remains readable in v2 for compatibility, while the user's current direction removes the action that creates new one-to-one same-book links.
3. **The original notebook is the passage-comment workflow.** It unifies paragraph comments and notes on highlighted excerpts, rather than having separate “comments” and “notebook” concepts. Iteration 20 now presents these together while retaining their separate persisted record shapes for compatibility.
4. **Original favorites are not separate named lists.** They are one collection with user-defined tags, multi-tag assignment, filter, and sort. Iteration 16 follows that model; named lists would be an additional feature and remain out of scope unless the project explicitly requests them.
5. **The original has more than a reader toolbar.** Word exports, keyboard modes, shelf management, statistics, and storage/recovery make up substantial parts of its product promise; the parity checklist must not treat them as incidental polish.

## User-reported prototype defects to carry into acceptance tests

- TTS depends on installed browser/OS voices and was not acceptable on the user's machine. If recreated for parity, expose that dependency honestly and evaluate it before deciding whether to keep it.
- OCR-derived Markdown lost the source-page sequence (585 PDF pages became about 508 text pages) and merged footnotes into ordinary text. Iteration 15 now matches the original for structured Markdown/HTML/DOCX footnotes: it moves each definition to its reference page, numbers by first reference per page, and repeats the note for references on multiple pages. This does **not** yet recover unmarked footnote text from OCR output; the actual Mistral marker/footnote syntax still needs a representative fixture. Tests must include blank/short pages and explicit printed page labels.
- Blank pages explicitly represented in Markdown (`sr:page` markers) are preserved, and DOCX hard-break pagination now retains empty pages indicated by consecutive explicit breaks. Consecutive layout-derived DOCX hints do not imply blank pages. Real-book/browser QA and preservation of the user's OCR marker format remain outstanding.
- Original page-range behavior is more than a page counter: the engine detects a paragraph fragment at the end of a page and its continuation at the next page, joins it for copying, and cites the full page range. Iteration 13 implements this for DOCX hard/layout page breaks in v2 and keeps the fragment UI addressable as one passage; a real-browser regression is still needed. Numeric OCR page markers missing from input are not enough to infer whether a page was blank or intentionally omitted. Preserve explicit blank-page markers and test skipped labels before synthesizing page surfaces.
- Markdown tables did not render as expected in the tested prototype. The v2 fixture covers tables, but it still needs visual browser comparison.
- A PDF screenshot showed the page number in the center of the page. The original viewer's code uses a centered placeholder while the PDF canvas is absent; reproduce this observation with the user's PDF before deciding whether it is a loading-state defect or a persistent rendering problem.
- Library navigation, citation presentation, and save-status flicker also need explicit browser acceptance, not just source-code review.
- Keep the user's requested UX adaptations separate from original parity: cream/low-glare theme, non-blocking notifications with undo, stable save-state display, quick passage tagging, and PDF passage navigation/highlighting. The request for PDF++-style export to another note remains a scope question because the intended destination was not specified; internal collection/comments are not the same as external note handoff.

## Recommended implementation order after this audit

1. Finish the current reader's browser acceptance: two toolbars, outline, page/footnote/table/image fixtures, persistence, page-range citations, and explicit blank-page behavior.
2. Reconcile remaining study semantics with the original: Favorite tags/filter/sort, category-to-color behavior, category-filtered reader search, the unified notebook list, and cross-book link groups are implemented. Same-book link creation is removed per the user's review; keep old records readable. Keep the user's non-modal comment placement and no-audio-storage changes.
3. Finish citation-output edge cases and browser verification, then verify the iteration 29 statistics/report download in the whole-app review.
4. Restore library organization/import formats and Word/JSON exports through adapters and application workflows.
5. Design native PDF separately from structured-book reading; decide whether OCR remains an external import workflow or becomes an in-app feature before selecting an OCR engine/provider.
6. Recreate the remaining reading modes, keyboard shortcuts, tabs/split view, portability, and onboarding. Keep AI/Claude/integrations deferred as already agreed.
7. Only after feature-level comparison, review explicit `[?]` items with the project decision group and prune unwanted features.

## Architecture implication

The original's single-file implementation is useful as behavioral evidence but is not a structure to copy. The v2 target remains a layered modular monolith. Before the audit backlog grows, move study workflows out of `App.tsx`: keep domain rules pure, introduce application services for study/citation/navigation, and let UI components call those services. Build each importer, PDF viewer, clipboard/export, and storage/sync path as an adapter around shared domain contracts. No backend or microservices are required for this structure.
